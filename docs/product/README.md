## Заказ Bitrix → продажа TicTacToy

Сопоставление в карточке заказа использует тот же серверный каскад
`SharedCatalog`, что и форма продаж: активный бренд → его категория → активный
товар из `catalog_excel_products`. Поиск выполняется на сервере по названию,
артикулу и штрихкоду; нулевой остаток не скрывает товар. В HTML не встраивается
полный каталог, а выбранная запись восстанавливается запросом по ID.

Связь хранит отдельно стабильный `bitrix_product_id` товара/предложения,
`bitrix_sku_id`, диагностический `bitrix_order_line_id`, внутренние `product_id`,
`brand_id`, `category_id` ERP и необязательный `moysklad_product_id`.
Переименование не ломает связь. Старые записи только с `moysklad_product_id`
сохраняются и разрешаются через единый каталог лишь при однозначном совпадении;
неоднозначные, отсутствующие и архивные связи требуют ручного выбора. Поэтому
разрушающая миграция `product_mappings.json` не нужна.

Подтверждение статуса `A` само остаток не меняет. Отдельное проведение создаёт
одну запись `erp_sales`, несколько `erp_sale_items` и движения по каждой строке
в одной SQLite-транзакции. Количество одинаковых товаров проверяется суммарно,
а снимок названий, идентификаторов, цен и данных заказа сохраняется в продаже.
Источник истины для этой операции — локальный каталог ERP; отдельное списание
МойСклад и legacy JSON-операция не создаются.

Повторное проведение защищено нормализованным источником `tictactoy`, внешним
ID заказа, idempotency key, повторной проверкой внутри `BEGIN IMMEDIATE` и
условным обновлением `stock >= quantity`. Отказ проведённого заказа блокируется:
сотрудник сначала отменяет связанную продажу штатным механизмом, который
возвращает остаток обратным движением и сохраняет историю.

### Проведение без сверки сумм Bitrix

Флаги `calculation_complete` и `calculation_consistent` остаются диагностикой
и не ограничивают проведение. Отсутствие скидки, стоимости доставки или общей
суммы Bitrix, как и любое расхождение итогов, не блокирует продажу. Частичная
загрузка с единственной причиной `sync_missing=["total"]` также допустима.
Продажа использует существующие позиции, количества и цены ERP без подгонки
под итог Bitrix. Проверки статуса, состава, сопоставления, количества, остатков,
повторного проведения и прочих ошибок загрузки сохраняются.

Новые товары сотрудники добавляют через «Товары → Добавить из Bitrix».
Ручное создание отключено: POST `/warehouse/add`, `/api/products`,

Общие сервисы каталога, существующие импорты, редактирование карточек,
фотографии и складские операции сохранены. Проверка контракта:

и `tests/test_stage2_products_api.py`; внешние клиенты в тестах подменены.

## Добавление количества из Bitrix (2026-09-08)

В «Товары → Добавить из Bitrix» пользователь вводит целое положительное
количество (`quantity` в POST `/api/v1/bitrix-products/<id>/import`).
Новая карточка создаётся с нулевым остатком; введённое количество проводится
штатным приходом в той же транзакции. У существующей карточки не обновляются
название, бренд, категория, цена и фотографии: добавляется только количество.
Оба прежних значения `action` (`create`, `update`) используют этот контракт.
При передаче проверенного `supply_id` API только разрешает карточку
(`resolve`), без начисления количества; приход выполняет документ поставки.
Остаток Bitrix показывается справочно и не участвует в начислении.

Matching использует связь с Bitrix ID (включая catalog product), затем XML ID
и артикул; неоднозначные и конфликтующие связи отклоняются. По названию
товары не сопоставляются. Поставки сохраняют свою механику документов,
проведения и идемпотентного дополнения; повторное проведение не начисляет
остаток, изменение проведённого документа через update отклоняется.
Проверки: `test_single_bitrix_product_import.py`, `test_supplies.py`.
Миграций и коррекции существующих остатков не требуется.

### Сохранённое production-поведение импорта (2026-09-15)

Создание карточки из Bitrix допускает количество 0: товар сохраняется без
прихода и движения остатка. Повторный запрос с 0 возвращает существующую
карточку. Для добавления количества существующему товару (`action=update`)
по-прежнему требуется положительное целое количество. Это поведение уже
работало на production и сохранено при объединении с PR #524.

### Склад интерактивного импорта (локальная правка, 2026-10-05)

В «Товарах → Добавить из Bitrix» назначение прихода берётся из выбранного
склада и явно показывается в окне. В режиме «Все склады» требуется выбрать
конкретный склад; суммарный остаток не является местом прихода. POST передаёт
`warehouse_id`, сервер проверяет активность склада и сохраняет его в документе,
метаданных и движении. После сохранения открывается тот же склад. Отсутствующее
поле старого API-клиента по совместимости означает TTT; явно пустой, неизвестный,
отключённый склад или `all` отклоняются, без подмены на TTT.

Карточка и Bitrix-связь общие для всех складов: повторное добавление использует
существующий товар и начисляет только введённое количество выбранному складу.
Остаток Bitrix остаётся справочным. Нулевое количество сохраняет карточку без
прихода; количество, уже учтённое на TTT, переносится документом перемещения,
а не новым приходом. Импорт из поставки по-прежнему только разрешает карточку;
склад и начисление определяются самой поставкой.

Числовой запрос ищется и как Bitrix ID, и как название/артикул; точный ID идёт
первым, совпадения не дублируются. Выключенные на сайте товары доступны для
поиска: активность витрины не определяет возможность складского прихода.
Проверки: `test_bitrix_catalog.py`, `test_single_bitrix_product_import.py`,
`test_supplies.py`, `test_multiwarehouse.py`. Миграций нет; этот раздел описывает
локальную правку, а не подтверждённый выпуск на production.

## Мультисклад в карточке и истории (2026-10-05, локально)

Локальное уточнение 2026-10-06 заменяет «Другие склады» на выпадающий выбор
склада и остаток выбранного склада в одной строке. TTT первым в списке;
при открытии из конкретного склада выбран он, а из «Все склады» — TTT
(это не суммарный остаток). Меню содержит все возвращённые API склады,
включая нулевые, и открывается поверх карточки. Оно ограничено по высоте,
прокручивается отдельно и не сдвигает настройки/кнопки. Выбор внутри карточки
сохраняется при обновлении после сохранения того же товара, но не переносится
на другой товар или другой складской контекст каталога. Количество «В пути на склад»
отображается только при наличии отправленного, но ещё не принятого перемещения
и не прибавляется к доступному остатку получателя. Неактивный склад с остатком
не скрывается; неподтверждённый физический остаток TTT не выдаётся за ноль.
Данные читает GET `/api/v1/products/<id>/warehouse-stocks`, без складских записей
или обращения к Bitrix. Ошибка загрузки показана явно, без подстановки нулей.

Локальное продолжение 2026-10-06: в режиме редактирования под выбором склада
одно поле «Остаток <название склада>». Оно меняется вместе с выбранным складом;
до загрузки, при ошибке, для отключённого склада, физического компонента или
сборного SKU корректировка отключена. Права не расширены: ручная корректировка
по-прежнему доступна администратору. Несохранённое изменение блокирует смену
склада до сохранения или отмены; выбор того же склада не сбрасывает черновик.

PATCH карточки передаёт `stock`, `stock_warehouse_id`, `stock_expected` и причину.
В транзакции проверяются активность склада, блокировка инвентаризации,
допустимость товара, целое неотрицательное количество и совпадение исходного
остатка. При конфликте сохранение отклоняется без записи; нужно перечитать
карточку. Новый остаток записывается только выбранному складу через общий
`write_balance`, с движением `manual_adjustment`, причиной и пользователем в
истории/журнале. TTT и транзит при корректировке Гонконга не меняются.
Повтор старого запроса не создаёт второе движение; сохранение без изменения
количества не отправляет складскую корректировку. Корректировка и общие поля
сохраняются атомарно; изменение фото с корректировкой нужно сохранять отдельно
из-за внешней синхронизации фотографии. Старые API-вызовы без складского
контекста сохраняют прежнее назначение TTT. Миграций и публикации нет.
Проверки продолжения: 21 тест карточки/складского API (включая Node-проверку),
22 регрессионных теста API товаров и 16 структурных тестов прошли. Локальный
браузер подтвердил Гонконг 105 → 106 при неизменном TTT 0, запись истории,
защиту несохранённой корректировки, отмену и компоновку desktop/390/320 px.
