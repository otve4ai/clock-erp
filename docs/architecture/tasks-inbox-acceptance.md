# Входящие: принятие обычных задач и выполнение микрозадач

Статус: вариант для локальной пользовательской проверки, 2026-09-27.
База: `ef2f4308e017f320bbb42218650c4e7551b98f19`. Отдельный commit;
production, push, merge и deploy в эту работу не входят.
Уточняет прежние контракты Inbox в Stage D/E; схема v4 не меняется.

## Поведение

- Обычное создание поручения другому: `waiting` («Ожидает принятия»).
  Самому себе: `new` («К выполнению»), без входящего. Явно заданные статусы
  существующего create API сохранены, кроме `new` для поручения другому.
- «Ознакомиться» открывает отдельную карточку без редактирования, удаления,
  переназначения и автоматического read. Предпросмотр не меняет данные.
- `POST /api/v1/tasks-module/tasks/{id}/accept`, JSON `{version: N}`:
  только текущий исполнитель обычной активной задачи, только при наличии
  текущего незакрытого назначения. BEGIN IMMEDIATE → проверка прав/version/
  pending assignment → CAS task (`in_progress`, version+1) → Activity
  `status_changed` с `action=accepted` → закрытие Inbox → COMMIT.
  Любая ошибка откатывает всё; повтор со старой version → 409, без новых событий.
  Можно принять старое незакрытое поручение, уже имеющее `in_progress`:
  статус остаётся тем же, принятие отдельно фиксируется в Activity.
- Общие PATCH/status и прежние права редактирования сохраняются. Перевод
  обычной задачи в работу или завершение также закрывает назначение.
  Переназначение активной обычной задачи другому возвращает `waiting`,
  назначение действующим пользователем самому себе — `new`.
- Micro: `new/done`, неизменные 24 часа от создания. Во входящих только
  «Ознакомиться»; в preview нет завершения. Завершение доступно в рабочем
  списке/разделе микрозадач. Никаких принятия/прочтения. Незавершённое поручение остаётся
  во входящих, в том числе после срока. Done/deleted скрываются запросом;
  reopen/restore снова показывают действующее незакрытое назначение.
  Reassign закрывает старое поколение и создаёт новое; срок не продлевается.
  Самостоятельно созданные/назначенные себе микрозадачи не создают Inbox.
  Ранее существовавшая явная конвертация micro→normal сохранена.
- Старый `/inbox/{id}/read` возвращает 409 для активного незакрытого поручения,
  включая micro. Для уже обработанных/неактуальных событий сохранён idempotent read.
- List/count/notification claim используют JOIN текущей Task: совпадающий
  исполнитель, not deleted, not done, unhandled. Текущие title/type/version и
  micro deadline выдаются вместе с Inbox; snapshot не управляет действиями.
- Badge: `{count, normal, micro}`; dashboard сохраняет общий `inbox` и добавляет
  `inbox_counts`. Обычный красный счётчик и жёлтая `⚡` без числа разделены в меню,
  desktop/mobile sidebar и верхнем показателе. Нули скрываются.
- Inbox использует единую строку для normal/micro: иконка, три строки контента,
  общая action-сетка. Micro выделена молнией и подписью «Микрозадача · 24 ч».
  Компактный таймер без фона занимает слот кнопки принятия; точная дата и пояснение
  остаются в preview, в списке дополнительных строк нет. На узком экране общая
  action-сетка переносится под контент. Меню действий и резервного слота под него нет:
  справа ровно две колонки существующих действий/таймера.
- Inbox выдаёт micro раньше normal на backend, до LIMIT/OFFSET; внутри групп
  прежний порядок created_at DESC, id DESC. Счётчики и claim не меняются.
- Toast однократный, без повторов по таймеру; ссылка открывает ознакомление.

## Существующие данные — только перед возможным выпуском

`scripts/prepare_tasks_inbox_workflow.py` НЕ вызывается из HTTP/startup.
Сначала verified backup, остановленные writers и зафиксированный UTC cutoff.
Команда с `--database .../tasks-module.db --actor-id ADMIN_ID --before UTC_TIME`
делает только dry-run. `--apply` явно применяет одной локальной транзакцией:

1. Старое normal waiting с updated_at не позже cutoff → in_progress,
   version+1, history с `action=inbox_workflow_preparation` и реальным ID оператора.
   Старое ожидание ответа не представляется как новое принятие.
2. Ранее прочитанные активные micro возвращаются только для последнего события
   текущего исполнителя, если после его assignment version не было reassign.
   Удалённые/готовые, retired/self generations и записи после cutoff исключены.
   Повторный toast не создаётся; дедлайн не меняется.

Повтор безопасен/idempotent; ошибка Activity откатывает все записи. Схема,
ledger, FK, индексные определения и legacy DB не меняются. Команда доверенная
административная: actor-id задаёт оператор, это не HTTP endpoint.

## Обратимость и проверка владельцем

Локальный preview использует только временные synthetic DB и две тестовые
личности. В нём есть обычное входящее, активная и просроченная микрозадачи.
Фикстура позволяет тестам выбрать второго синтетического пользователя через
`X-Preview-Actor: 2` только для Tasks API; production auth этого не поддерживает.

Откат отдельного коммита возвращает прежний код и не требует downgrade схемы.
Он не должен восстанавливать рабочую БД поверх действий пользователей:
выполненные задачи, новые записи и история сохраняются. После возможного
production trial изменение смысла waiting и результаты offline preparation
нужно отдельно сверить по истории; «точный откат данных» автоматически не делаем.

До принятия владельцем проверка и trial выполняются локально, production неизменён.
Перед выпуском необходим повтор exact Linux/Python3.6.8/SQLite3.7.17 runner
на обновлённых исходниках; текущие локальные проверки его не заменяют.
