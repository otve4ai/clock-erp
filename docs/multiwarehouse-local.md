# Мультисклад: локальный пилот TTT + Гонконг

Статус: **draft / implemented-local**, 2026-10-05. Ветка
`codex/multiwarehouse-local`, база `origin/main` на `8f62841`.
Это не описание production и не разрешение на миграцию живой БД.
Локальная реализация выполнена без production-данных, `.env` и внешних
складских запросов. Владелец отдельно разрешил актуализацию ветки, commit,
push, Draft PR и CI; merge и deploy требуют следующего отдельного решения.

Актуальное решение владельца 05.10: сначала тестируем **один дополнительный
склад — Гонконг**, основной TTT сохраняется. WB подключается отдельным этапом.

## Что реализовано

- Переиспользованы сущности `erp_warehouses`, `erp_warehouse_stocks` и единый
  `catalog_stock_movements`. Карточки товаров не дублируются.
- В первом этапе создаются только TTT и Гонконг; другие существующие склады остаются сущностями БД.
  Существующие идентификаторы складов не переписываются.
- Поля совместимости `catalog_excel_products.stock` и физический остаток
  компонента теперь относятся **только к TTT**, а не к сумме компании.
  Для компонентов сохраняется прежнее разделение исторического и физического
  учёта; старые документы не переводятся на физический баланс задним числом.
- `component_inventory.document_warehouse/balance/write_balance` определяют
  склад по документу; явный склад проверяется. Старые вызовы относятся к TTT.
  Триггеры зеркалируют прямые SQL-записи TTT в таблицу остатков. Это защита
  совместимости, а не замена журнала движения.
- Приходы/дополнения/отмена прихода используют склад документа. Продажа и
  списание принимают `warehouse_id`; отмена и возврат используют исходный склад.
  Склад проведённой продажи нельзя поменять редактированием метаданных.
- ERP — единственный источник складских количеств (решение владельца 05.10).
  `BitrixStockSync` и CLI запрещают `apply`; сверка читает физический остаток TTT.
  Обычный импорт **новой** карточки из Bitrix сохраняет прежний процесс: точное
  начальное количество один раз зачисляется на TTT. Повторное обновление
  карточки сохраняет цены/описания/статусы сайта, но не перезаписывает ERP stock.
  При создании карточки через поставку начальный stock специально равен нулю:
  количество зачисляется документом, без двойного прихода. Обычная сверка
  статуса сайта (ACTIVE/INACTIVE) не менялась. Восстановление бренда не импортирует stock и явно сообщает
  `reconciliation_required` при расхождениях; начальное количество — документом прихода.
- WB не включён в новый складской процесс. Новая отгрузка WB
  и таблица `erp_wb_fulfillments` исключены, склад WB не создаётся. Старые WB
  продажи по умолчанию продолжают использовать TTT. Общая форма заказа позволяет
  явно выбрать Гонконг, а адаптер передаёт этот склад в обычную продажу;
  это не создаёт дополнительного WB-перемещения. Это сохранение прежнего процесса,
  не реализация будущего учёта FBS/FBW. Живые документы не изменялись.
- Новая продажа Amazon по умолчанию относится к Гонконгу; товарный picker,
  фильтры наличия и серверная проверка используют этот склад. Кэш picker
  разделён по складам. Явный склад сохранённого документа имеет приоритет:
  исторические продажи каналов остаются на TTT, если были учтены там.
- Выбор склада добавлен в ручную продажу, проведение заказа, новую поставку,
  списание и запуск инвентаризации. Выбор и серверная проверка используют
  конкретный склад, без автоматического добора с другого. Склад сохранённой
  поставки/проведённой продажи зафиксирован; возврат берёт его из документа.
- Инвентаризация Гонконга включает только учтённые там физические SKU, включая
  нулевые позиции после движений. Дельта и версия движений относятся к складу
  документа. Пересчёт/приход HK-компонента не подтверждает физический остаток
  TTT. Непроверенные позиции при завершении не обнуляются. Общая история
  подписывает склад; прежний контроль регулярности брендов явно относится к TTT.
- Аннулирование поставки не удаляет ledger: документ остаётся `cancelled`,
  а уменьшения записываются компенсирующими движениями. Сохранено существующее
  правило пропуска позиций с последующими продажами на том же складе; пропуски
  явно показаны в предварительной проверке и журнале. Это не полный откат
  поставки, если часть позиций пропущена.
- Перемещение: черновик → в пути → принято. Черновик можно отменить. Отправка
  вычитает источник, приёмка добавляет назначение. Отмена в пути запрещена:
  нужен подтверждённый физический приём и при необходимости обратное перемещение.
  Частичная приёмка пока не поддерживается.
- Компания = сумма остатков складов + незавершённые перемещения. Товар в пути
  не включается в фильтр «В наличии» и не доступен для продажи.
- Все строки перемещения выполняются в одной `BEGIN IMMEDIATE`, включая
  документ, баланс, ledger и записи общего журнала по товарам. Повтор статуса
  не меняет остаток; ключ создания связан с исходным payload, несовпадение
  отклоняется. Тип ledger пока `manual_adjustment`, точная причина задаётся
  `source_type=transfer`, `operation_kind=send/receive` и номером документа.
- Сборный SKU не перемещается как отдельный физический товар: перемещаются
  компоненты. Удаление карточки/категории и откат Excel запрещены, если есть
  товар на другом складе или в пути. История перемещений сохраняет карточку.

## Минимальные изменения экрана «Товары»

Сохранена таблица. Добавлен селектор склада (по умолчанию TTT) и маленькие
точки рядом с числом: Гонконг — оранжевая, TTT — синяя. В новом пилоте WB нет.
Нулевые отсутствующие остатки не создают точку. Подсказка/нажатие раскрывают
название, количество и путь. Только товар в пути обозначен контурной точкой.
В режиме отдельного склада фильтрация и счётчики выполняются до пагинации.
Гонконг показывает товары с учётной записью (в том числе нулевой после
движений) либо ожидаемым перемещением, без отдельного справочника ассортимента.

Колонка сайта называется «На сайте TTT», карточка редактирования — «Остаток
TTT». Они не притворяются статусом синхронизации Amazon/WB. Экспорт первого
этапа разрешён только для TTT; для другого выбранного склада кнопка отключена,
API возвращает явную ошибку вместо неверного файла.

В меню «Действия» добавлены «Перемещения» (`/warehouse/transfers`). API:
`/api/v1/receipts/transfers`, `/<id>/send`, `/<id>/receive`, `/<id>/cancel`,
`/products`. Используется существующая авторизация, CSRF и запрет записи
для роли только чтения. Реальных внешних запросов в этом сервисе нет.

Проверены поиском прямые SQL-записи, `write_balance`, `_restore_columns`,
создание/удаление карточек и вызывающие HTTP-пути в `app/` и `scripts/`.
Эта карта не означает завершение всех последующих этапов.

## Миграция и сохранность

Новая ordered-миграция `2026-10-04-multiwarehouse-v1`; старые checksum не меняются.
Дополнительный структурный manifest проверяется runtime-валидатором; DDL
в runtime-сервисы не добавлен. Новый checksum нормализует переводы строк.

Если другие склады пусты, каждый существующий остаток TTT сохраняется.
Если по старой агрегатной модели уже были отдельные остатки, миграция один раз
вычитает их из общего поля, сохраняет их по прежним складам и сверяет сумму.
Отрицательное расхождение останавливает миграцию с откатом её транзакции, а не
маскируется нулём. Старые продажи/списания/инвентаризации получают склад TTT;
продажи и движения повторно не проводятся. Нужна отдельная проверка старой
истории по каналам: миграция не угадывает, что историческая продажа Amazon
на самом деле относилась к Гонконгу.

На заполненных таблицах колонка FK добавляется nullable и затем заполняется;
триггер вставки назначает TTT старым вызывающим участкам. Это совместимо с
ограничением SQLite на `ALTER ADD REFERENCES` с ненулевым DEFAULT.

Для будущей выкладки: отдельный бэкап, остановленные writers, сверка каждого
SKU/физических компонентов и сумм до/после, повторный прогон и FK/integrity.
Общий `business_snapshot` сравнивает сумму компании и digest количества каждого
SKU, включая физические компоненты и путь. Компенсирующие ошибки между разными
SKU не скрываются общей суммой. Конфликт существующего кода HK с другим ID
или отключённым складом останавливает миграцию: сопоставление нельзя угадать.
Простой откат кода после новых перемещений недопустим: старая версия понимает
stock как агрегат. Восстановление БД требует остановки и согласования всех
операций после backup. В этом этапе ничего подобного не выполнялось.

## Что ещё необходимо до живого запуска

1. Browser QA (включая адаптивность, частичную навигацию и недоступную сеть),
   Linux/Python 3.6/SQLite 3.7 rehearsal, независимый review, затем отдельное
   решение владельца о выпуске. Публикация Draft PR и CI отдельно разрешена.
   Страницы пока проверены
   только через Flask-клиент и синтаксические проверки, не визуально.
2. До миграции production — backup, остановка writers, сверка начальных TTT/HK
   и суммы каждого SKU на разрешённом стенде. Синтетические тесты миграции
   не заменяют проверку фактических данных. Затем обязательные CI/preflight,
   отдельное разрешение на публикацию/merge/deploy по AGENTS.md.

Границы первого этапа: Excel-импорт прихода и Excel-экспорт товаров остаются
TTT; UI явно подписывает это, HK-экспорт не выдаёт ошибочный TTT-файл.
Приход HK оформляется новой поставкой. Старые каталожные отчёты показывают TTT,
а не сумму компании; отчётность по всем складам — отдельное расширение.
Блокировки инвентаризации пока общие по товару: консервативно блокируют
операции и на других складах. История старого Excel-каталога остаётся в своём
журнале, перепроведение старых операций и унификация истории не выполнялись.

За рамками первого этапа: склад WB и новый marketplace lifecycle. Для будущего
WB нужно раздельно учитывать канал, склад отгрузки (TTT/WB), состояние доставки
и свободный остаток. Приёмка FBS-заказа в логистику не равна свободному остатку
WB. Автоматические marketplace-события/отчёты также не входят в этот пилот.

## Локальные проверки

### Просмотр на своём компьютере

`python scripts/preview_multiwarehouse.py --port 4197` запускает
`http://127.0.0.1:4197/app/products` и `/warehouse/transfers` на новой временной
БД. Нужен Python 3.10+ с уже установленными зависимостями проекта.
Стенд содержит 1000 вымышленных товаров, остатки 15 SKU в Гонконге и три
учебных перемещения TTT ↔ Гонконг (черновик, в пути, принято). Данных WB нет.
Повторный запуск создаёт данные заново. Это демонстрация первого этапа,
не копия production и не полный тест всей ERP.

Скрипт не загружает `.env`, очищает настройки интеграций в дочернем процессе,
запрещает исходящие socket-подключения/подпроцессы, слушает только loopback.
CSP ограничивает запросы браузера этим стендом. Остальные HTTP-разделы и
операции записи, кроме перемещений, отключены. На страницах видна пометка
«Все данные вымышлены». Windows shim предназначен только для одиночного демо.
HTTP smoke: товары TTT/HK, перемещения, список документов и JS отвечают 200;
полное визуальное QA пока не выполнено.

`scripts/test_multiwarehouse.py` использует существующий no-egress harness,
временные синтетические БД, очищение интеграционных настроек. Никаких живых
данных. Windows fcntl-shim позволяет одиночный runner, **не доказывает** Unix
process lock. Опция `--manifest` генерирует структуру только на временной БД.

Проверки предыдущего этапа (04.10): `test_multiwarehouse.py` — 20, продажи — 124,
поставки — 30, ручные приходы — 7, компоненты — 16, списания — 10,
инвентаризация — 35, Excel-каталог — 25, статусы сайта — 2, переключатель
наличия — 2. Все эти 271 теста прошли на том этапе. Это не полный набор CI.
Новый набор покрывает повторные/конкурентные отправки, rollback, путь,
сохранение общего количества, миграцию заполненных продаж, повтор миграции,
сверку старого split и отказ при ошибке, HK-продажу/возврат/списание,
инвентаризационную дельту TTT, приёмку, CSRF/readonly и рендеринг страниц.

Runtime DDL gate (23 контролируемых модуля/manifest), Python/JS syntax,
JSON parse и `git diff --check` проходят. Общий `test_schema_migrations.py`:
18/21 успешно на этой Windows-среде; два preflight требуют отсутствующий
`sqlite3` executable, третий — настоящую Unix-блокировку. Эти проверки
не отключены и не объявлены успешными; полный CI/release preflight не пройден.

Успешно завершены целевые наборы: мультисклад — 21, marketplace warehouses — 11,
WB sales — 24, WB orders — 21, продажи — 124, поставки — 30, unified catalog API — 15,
Bitrix `*sync` — 33, восстановление бренда — 2. Всего 281 тест, не полный CI.
Это результаты предыдущего прототипа: новые WB-сценарии после решения владельца

Проверены также создание Amazon-продажи через HTTP при нулевом TTT и положительном
HK, сохранение склада в ответе/API отчёта и при редактировании примечания,
WB dispatch через HTTP (роль, CSRF, retry, недоверие клиентскому статусу/количеству),
изменение состава после отгрузки, сохранение старых движений при аннулировании.
Тестовые исторические продажи явно используют TTT; новая маршрутизация каналов
проверяется отдельно, история не маскируется изменением исходных остатков.

Runtime DDL gate, Python compile, проверки JS и `git diff --check` прошли.
Локальный демо-сервер перезапущен на новой синтетической БД; HTTP 200 проверены
для TTT/HK/WB, страницы перемещений и её API. Browser/E2E не запускались;
ожидание текста аннулирования в `frontend/e2e-supplies` обновлено.

Ограничения среды подтверждены повторно: schema migrations — 18/21, остальные
3 требуют sqlite3 CLI/настоящего Unix flock. В `test_wildberries_sync.py` две
проверки конкурирующих flock не проходят с Windows no-op shim. В
`test_sales_receipts_enhancements.py` 2/3, PDF-тест остановлен отсутствием
`reportlab`. Это не успешные проверки и не основание для выкладки.
