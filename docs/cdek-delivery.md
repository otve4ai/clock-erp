# Статусы доставки СДЭК

Статус: `active`. Базовая интеграция выпущена 2026-10-01 в PR #635; последующие изменения интерфейса проходят отдельный выпуск.

## Поведение

### Единая карточка работы с клиентом — 2026-10-08, локально

Карточка сохраняет заказ, накладную, способ доставки, товары, статус, причину
внимания, обновление и время проверки СДЭК. История доставки показывает три
последних события, остальные раскрываются отдельно от общения.

Одна форма объединяет новый звонок (по умолчанию «Не фиксировать»), общий
комментарий, статус и условные поля. Для «В работе» доступны свободный текст
следующего действия и дата; для «Обработан» — результат. Добавлен результат
«Не удалось связаться»; для него и «Другое» обязателен общий комментарий.
Звонок в новой форме датируется временем сохранения в МСК. Старые записи с
заданным временем и прежние пояснения сохраняются. Комментарий после успеха
очищается для нового действия; последняя заметка остаётся в таблице и истории.

Сводка читает фактические журналы. Email открывается в существующей почте,
текст SMS доступен для чтения, отправка SMS открывает существующую форму.
История объединяет менеджерские записи со связанными звонками, исходящими
email/SMS; три последних записи видны сразу. Отправленные сообщения не
считаются прочитанными. Автоматический email определяется по ключу напоминания;
имя автора SMS берётся из журнала, у ручного email показывается ID сотрудника,
если журнал не хранит имя. Неизвестный автор не выдаётся за автоматику.

Сохранение не вызывает отправку сообщений или изменение статусов СДЭК.
Версия защищает от потери параллельных изменений; хеш запроса с автором
в истории распознаёт точные повторы без второго звонка. Все поля сохраняются
при ошибке в той же карточке, ошибки обязательных полей выводятся рядом.
Закрытие текущей работы и возврат внимания при новых событиях остаются прежними.
Нижняя панель закреплена, на мобильном поля переходят в одну колонку.

Проверка: временные хранилища и подменённые интеграции; preview
`tests/cdek_manager_preview.py` на 127.0.0.1:5064 не использует реальные данные.
Изменения требуют отдельной публикации и развёртывания.

### Уведомления: согласованная схема 2026-10-07

Автоматизируется только email через 3 полных суток после поступления в ПВЗ.
Дополнительная защита от 2026-10-07 подготовлена локально и требует выпуска:
перед очередью и SMTP допускаются только тарифы до ПВЗ 136, 138, 232, 234,
непустой код пункта и `type=PVZ` в справочнике офисов. Тарифы до двери
137, 139, 231, 233 исключены; неизвестные/отсутствующие тарифы и постаматы
также не получают письмо. Источник тарифов: https://apidoc.cdek.ru/.
Смена доставки на курьерскую после очереди блокирует SMTP. Неизвестный способ
и конфликт тарифа с ПВЗ показывают «Проверить способ доставки», без причины
«Не забирают». Для курьерской доставки карточка предлагает звонок при проблеме.
Кеш содержит только категорию доставки, без адреса получателя; старый кеш
требует обновления. GET интерфейса не обращается к API.
Перед отправкой требуется актуальная проверка через API СДЭК; полученные,
отменённые и возвращаемые отправления исключаются. Повторное письмо для того
же поступления не отправляется. Данные ПВЗ, статус, дата поступления и доступный
подтверждённый срок хранения берутся из API СДЭК; отсутствующие поля не выдумываются.
Текст письма согласован 2026-10-07. Автоматизация реализована локально в
`app/services/cdek_reminders.py` и подключена к существующему `scripts/mail_worker.py`.
Публикация и включение на сервере ещё не выполнены.

Для включения при отдельном выпуске: `CDEK_EMAIL_REMINDERS_ENABLED=1` в окружении
существующего почтового worker; требуются подключённая почта, ключ СДЭК, общий
`CDEK_CACHE_DIR` и актуальный кеш продаж от фоновой синхронизации СДЭК. Без флага
обычная почта работает как раньше, автоматические напоминания не отправляются.
Новый таймер не нужен: используется расписание существующего почтового worker.
Cron передаёт `--environment-file /etc/clock-erp/clock-erp.env`; worker проверяет
владельца root и права 0600, загружает только почтовые/CDEK настройки и путь
snapshot заказов. Секреты в вывод и аргументы процесса не попадают.

Кеш используется только для отбора кандидатов. Перед постановкой и перед SMTP
выполняется свежий `GET /v2/orders` по точной накладной; адрес и график берутся
через `GET /v2/deliverypoints?code=...` с точным совпадением кода ПВЗ.
Контракт: [документация API СДЭК](https://apidoc.cdek.ru/#tag/delivery_point).
Email и имя получателя берутся из `recipient` СДЭК; без однозначного email или
адреса ПВЗ письмо не ставится в очередь (счётчик ошибок в журнале worker).
График без данных пропускается. Поле подтверждённого срока хранения в используемом
ответе пока не верифицировано, поэтому строка «Забрать до» не выводится.
Постаматы исключены: согласованный шаблон предназначен для пункта выдачи.

Отсчёт — 72 часа от начала непрерывной последовательности статусов готовности
к выдаче. Ключ `cdek-pvz-v1:<накладная>:<момент поступления>` уникален в mail_outbox;
запись и привязки заказов сохраняются одной транзакцией. Системный автор — 0.
Повтор после SMTP timeout/неопределённого результата запрещён, ручная почта сохраняет
свою прежнюю обработку. Сбой API перед SMTP оставляет письмо в очереди с кодом
`CDEK_RECHECK_PENDING`; потеря актуальности завершает его без SMTP с кодом
`CDEK_REMINDER_NOT_APPLICABLE`. Перед отправкой адрес и текст обновляются по API.
Проверка актуальности непосредственно предшествует SMTP, но атомарная транзакция
между СДЭК и почтовым сервером невозможна.

Один проход готовит не более 20 кандидатов с бюджетом 60 секунд плюс текущий
API-запрос; отдельный такой же бюджет действует на проверки перед SMTP.
Курсор `CDEK_CACHE_DIR/email-cursor.json` содержит только ID групп продаж и
не позволяет записям без email постоянно задерживать остальные. Его обновляет
почтовый worker под существующим process lock. Полные ответы СДЭК и контакты
не добавляются в кеш доставки; адресат и готовый текст находятся в почтовом журнале.
На первом включении проверяются в том числе ранее поступившие незабранные заказы.

Тема: «Ваш заказ TicTacToy.ru ждёт вас в СДЭК ❤». Тело содержит согласованное
приветствие, номер заказа, адрес ПВЗ, доступный график, накладную, дату поступления,
ссылку на СДЭК и подпись команды TicTacToy.ru. SMS этот worker не вызывает.

Проверено локально: 104 теста в модулях CDEK и почты, 103 успешны, один POSIX-тест
прав доступа пропущен на Windows. Сценарии включают параллельную постановку,
получение после постановки в очередь, ошибки API и неопределённый результат SMTP.
Проверки синтаксиса, diff и runtime DDL пройдены. Linux migration_preflight
на Windows не запускается из-за отсутствия fcntl; перед выпуском требуется CI.
Реальные СДЭК/SMTP в тестах заменены mock-клиентами, письма клиентам не отправлялись.

Автоматическая SMS через 6 дней отменена. SMS отправляет менеджер вручную.
В карточке добавлен переход «Перейти к отправке SMS» в `/app/sms?compose=1`
в новой вкладке, чтобы сохранить незавершённые заметки в карточке. Если связан
ровно один ID заказа, он передаётся в существующую форму; иначе менеджер
выбирает заказ или ищет получателя по накладной. Переход не отправляет сообщение:
менеджер проверяет получателя и текст и нажимает кнопку отправки в Центре SMS.
Права доступа и отправки проверяются существующим разделом SMS.

Согласованный текст SMS: `{client_name}, Ваш заказ TicTacToy.ru ожидает получения ❤ Трекинг {tracking_number} Отследить cdek.ru.`

### Продажи и сверка

На вкладке Tictactoy появился компактный столбец «СДЭК» после трекинга
(включая адаптацию ранее сохранённого порядка столбцов). Кнопка «Сверка СДЭК»
со счётчиком проблем доступна в Tictactoy и «Все продажи».
Экран `/sales/cdek` по умолчанию показывает проблемные отправления. Есть
общие счётчики, только срочные, категории, поиск по заказу/накладной,
отметки менеджера, страницы по 25/50 строк. Фильтры не изменяют общие счётчики. Верхние счётчики открывают соответствующий
статус или все проблемные отправления, сбрасывая поиск и остальные фильтры.
Во вкладке «Все отправления» без категории ни одна категория проблем не выделена.
Кнопка «Обновить СДЭК» внутри сверки запускает тот же защищённый фоновый пакет,
что и панель продаж; после завершения список обновляется с сохранением фильтров.
Возврат к продажам сохраняет исходные параметры поиска, периода и страницы.
Данные перевозчика и пользовательский текст экранируются; URL возврата
разрешён только для локальных `/sales` и `/app/sales`.

Столбец «Дата заказа» использует дату из продаж ERP (`created_at`); для
объединённых строк берётся самая ранняя известная дата, с приведением явного
часового пояса к МСК. Доступна сортировка по номеру и дате в обе стороны до
пагинации; отсутствующие значения остаются в конце. По умолчанию — срочные.
Сортировка сохраняется при фильтрации, переходах страниц и сохранении отметки.
Под статусом отображается дата события СДЭК, время проверки — в подсказке.
«В пути» — синий, «В ПВЗ» — жёлтый, «Вручён» — зелёный, проблемы доставки —
красный, отсутствие данных — серый. Цвета адаптированы к светлой/тёмной теме.
Номер заказа ведёт в его карточку ERP через точное сопоставление с локальным
снимком заказов Tictactoy. Если однозначного совпадения нет, открывается поиск
по номеру в ERP. Несколько заказов одной накладной имеют отдельные ссылки.
Карточка отправления открывается справа кнопкой «Открыть». Закрывается
крестиком, кнопкой или Escape. История доставки раскрыта по умолчанию: пять последних событий и раскрытие остальных;
кнопки закрытия и сохранения закреплены внизу. POST, CSRF и версии отметок
сохранены; закрытие возвращает фокус к строке списка.

Источник — тот же `api_sales_records`, что используется продажами: ручные
продажи, складские операции и исправления трекинга. Одна явно указанная
накладная объединяет товарные строки; без трека используется номер магазина.
Для продаж отдельный ключ кеша зависит от ссылки на отправление, а не от ID
товарной строки. Изменение трека не переносит прежний статус и заметки.
Остальные каналы не запрашиваются. Отменённые продажи без трека исключены.
GET читает кеш; ручное обновление — защищённый POST, плановое — CLI.

Сверка содержит все незавершённые отправления; вручённые — за 30 дней.
Старую вручённую накладную можно открыть напрямую из продажи. Категории
проблем пересекаются, но общий счётчик считает каждую накладную один раз.
Отсутствие ключа, неизвестные статусы, ошибки поиска, связи и старые данные
отображаются явно, не превращаются в «всё в порядке».

Правила: от 3 полных суток в ПВЗ — внимание, от 5 — срочно; последовательные
события готовности к выдаче не сбрасывают отсчёт. От 3 суток без новых событий
в пути — проверка. Промежуточный возврат на склад не означает возврат клиентом.
Порогами управляют `CDEK_PVZ_WARNING_DAYS`, `CDEK_PVZ_URGENT_DAYS`,
`CDEK_TRANSIT_WARNING_DAYS` (1–60 дней, срочный порог не ниже предупредительного).

Срок хранения и обещанная дата доставки не выводятся из предположений:
ранее внесённые подтверждённые СДЭК даты сохраняются, поле ввода убрано из карточки. Дата хранения действует до
конца указанного дня по МСК; за сутки до неё — срочно. Просроченная
подтверждённая доставка также срочная. Автоматическое получение этих двух
дат из API пока не реализовано; без даты отображается «срок уточнить».

Менеджер сохраняет комментарий и статус: «Нужна реакция», «В работе»,
«Обработан». Для завершения обязателен результат: получение заказа, отказ,
проверка возврата или другое с пояснением. Проверка возврата доступна только
при is_return + DELIVERED/POSTOMAT_RECEIVED; статус перевозчика не изменяется.
Старое closed читается как «Обработан / Возврат проверен». При следующем
сохранении исходная отметка включается в историю, комментарии сохраняются.

Обработанные ситуации исключаются из активной очереди и счётчиков проблем,
включая прежние ошибки связи; ошибка обновления остаётся видна в карточке.
Все отправления доступны за всё время, счётчик вручённых ограничен 30 днями.
Фильтр «Обработан» переключает список во «Все отправления». Открытая карточка
остаётся доступной после исчезновения строки из текущего фильтра.

«В работе» поддерживает необязательные next_action и followup (дата МСК).
С наступлением даты эффективный статус становится «Нужна реакция», запись
попадает в проблемы. Смена срока сохраняет прежнее значение в истории.
Перевод в завершённое состояние отключает напоминание. Старые today/tomorrow
не создают новых напоминаний; старый срок сохраняется как legacy_followup.

Повторное внимание определяется по значимым этапам: ПВЗ, невручение, начало
возврата и получение возврата. Более новое событие другого этапа относительно
закрытого снимка открывает реакцию. Повтор того же этапа, обновление времени
проверки, названия или города не открывает обработку. Результат и история
предыдущей работы сохраняются. Вычисление очереди не записывает данные при GET.

Последние столбцы: комментарий → контакты → обработка → открытие карточки.
Email/SMS читаются из существующих sms_messages и mail_outbox/mail_links,
строго по ID заказа и только при одной накладной на этот ID. Без однозначной
связи (включая старые SMS, отправленные напрямую по накладной без order_id)
показывается «Нет данных». Поиск по тексту сообщения, номеру телефона или
похожему номеру заказа не используется. Ошибки чтения не имитируют отправку.
Принятие провайдером отображается как «Отправлено», а не доставлено/прочитано;
ошибка провайдера — «Ошибка». Отсутствие истории отличается от черновика/
неотправленной записи. Для вручённых/отменённых без контактов — «Неприменимо».
Индикаторы обновляются чтением локальных журналов каждые 30 секунд; новые
API-вызовы провайдеров и отправки из карточки не выполняются.

Звонки добавляются к истории с результатом, фактической датой/временем МСК,
менеджером и комментарием. В таблице — последний по времени звонок, а не
последняя внесённая запись. Подсказки доступны мышью, клавиатурой и нажатием.
В карточке история доставки находится выше контактов и формы менеджера;
подтверждённый срок хранения показывается короткой строкой. Самостоятельный
блок сроков удалён, расчёты срочности используют сохранённые даты.

Локальные отметки хранятся в `CDEK_CACHE_DIR/reviews`, атомарно под тем же
межпроцессным lock. Версия записи предотвращает потерю параллельных правок;
при конфликте показывается несохранённая заметка. Миграций БД нет.
Доступ и изменения разрешены admin/employee через текущие проверки прав
ERP; POST дополнительно проверяет CSRF и наличие отправления в продажах.

### Карточка заказа

В карточке заказа Tictactoy добавлен блок «СДЭК»: накладная, исходный статус
перевозчика, город, дата события и история доставки. Время отображается в МСК.
Кнопка обновления доступна при настроенном ключе; GET карточки читает только
локальный кеш и не вызывает СДЭК. Ошибка связи сохраняет предыдущий статус,
показывает предупреждение и дату последней успешной проверки.

Запрос сначала использует явно заданную накладную из трекинга, иначе номер
заказа магазина. Ответ должен точно совпасть с запрошенным номером.
Поле трекинга, оплата, склад, бизнес-статус заказа и данные Bitrix не изменяются.
Wildberries исключён. Персональные данные получателя не сохраняются в кеше.
Из истории исключаются удалённые события, остальные сортируются по времени.
Возвратная накладная помечается отдельно. Несколько накладных на один заказ
пока не объединяются: при повторном использовании номера магазина следует
указать нужную накладную явно.

## Настройка и запуск после разрешения на выпуск

Переменные окружения web-процесса и фонового процесса:

- `CDEK_ACCOUNT` — Account из личного кабинета;
- `CDEK_PASSWORD` — Secure password;
- `CDEK_CACHE_DIR` — общий постоянный каталог кеша (по умолчанию `instance/cdek`);
- `ORDERS_DATABASE_PATH` — существующая база snapshot заказов;
- `CDEK_ORDER_OVERRIDES_PATH` — путь к локальным исправлениям трекинга для CLI
  (по умолчанию `instance/order_overrides.json`).

Секреты передаются через защищённую конфигурацию окружения сервера; в Git,
аргументы командной строки, JSON-ответы ERP и журналы их помещать нельзя.
Ключ считывается при старте процесса. Смена конфигурации требует перезапуска
web-процесса. Нового ключа, подписок и отправлений интеграция не создаёт.

Разовый запуск: `python -m scripts.cdek_delivery_sync`.
Подготовлены `deploy/systemd/vechasu-cdek-sync.service` и `.timer` по принятой
в проекте схеме WB. Перед установкой нужно проверить пути текущего release,
Python и EnvironmentFile на сервере и обеспечить один общий кеш для web и CLI.
Сервис и таймер автоматически этим изменением не устанавливаются.

CLI читает канонический список продаж через модуль приложения, затем только
карточки, для которых уже выполняли ручной запрос СДЭК. Полный архив snapshot
не ставится в очередь: это предотвращает задержку обновления продаж тысячами
старых заказов. Кеш карточек сохраняет прежний формат; одна накладная может
иметь отдельный кеш карточки и продаж. Несколько товарных строк продаж
не вызывают повторных запросов. Обоим процессам необходим один каталог кеша.

Таймер запускает проверку каждые 60 минут. Один проход ограничен 100 записями
и приблизительно 180 секундами плюс один текущий HTTP-запрос. Активные
отправления проверяются с интервалом от 60 минут, завершённые — раз в сутки,
ошибки поиска — не чаще раза в час. При большом числе заказов обновление может
занять несколько проходов; необработанные выбираются раньше проверенных.
HTTP 429 и ошибки авторизации/сети останавливают текущий пакет.
Ручные повторные запросы в течение минуты используют предыдущий результат.

Кеш — отдельные атомарно заменяемые JSON-файлы под общим межпроцессным lock;
миграция существующих баз не нужна. Повреждённый JSON не затирается.
Откат: остановить таймер, вернуть предыдущий release. Кеш можно оставить;
заказы и внешние системы изменений не получают.

## Проверки и ограничения

- Базовая интеграция PR #635 прошла Linux CI и была развёрнута 2026-10-01.
- На production systemd 219: вместо неподдерживаемого `ExecCondition`
  используется `ConditionPathExists=!/run/clock-erp-maintenance.json` в drop-in.
  При выпуске интерфейса настройки службы, таймера и секреты сохраняются.
- 53 целевых теста CDEK: API, кеш, группировка, сроки, права, CSRF, конфликты,
  сортировки, пагинация, экранирование. Локальный UI проверен на тестовых данных:
  цвета статусов, боковая карточка, открытие, закрытие, Escape, дата заказа.
- Вебхуков нет; используется polling. Подтверждённые даты хранения и доставки
  сохраняются из прежних отметок менеджеров. Изменения интерфейса не требуют миграций или смены ключа.

### Панель обновления в продажах

Кнопка «Сверка СДЭК» на вкладках «Все продажи» и Tictactoy раскрывает панель
в общем стиле сверки товаров. Внутри — переход к проблемным отправлениям,
ручной запуск, результат и время последнего запуска/успеха (МСК), кнопка «Все отправления» и расписание проверки каждые 60 минут. Ошибки синхронизации отделены от
проблем доставки. Панель опрашивает локальный статус, GET не вызывает API СДЭК.
POST защищён правами и CSRF; пакет выполняется в фоновом потоке. Ручной запуск
проверяет и недавно завершённые накладные, сохраняя защиту повторных запросов 60 с.
CLI и ручной пакет используют общий межпроцессный lock и атомарный журнал в
CDEK_CACHE_DIR/batch. Прерванный процесс определяется по освобождённому lock.
Лимиты пакета и бюджет времени прежние; таймер проверяет отправления в начале каждого часа. Активные статусы считаются
устаревшими через 2 часа без обновления; ручная проверка доступна между запусками.
