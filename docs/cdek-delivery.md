# Статусы доставки СДЭК

Статус: `draft` — реализовано и проверено локально; публикация и production ещё не выполнены.

## Поведение

### Продажи и сверка

На вкладке Tictactoy появился компактный столбец «СДЭК» после трекинга
(включая адаптацию ранее сохранённого порядка столбцов) и кнопка «Сверка СДЭК».
Экран `/sales/cdek` по умолчанию показывает проблемные отправления. Есть
общие счётчики, только срочные, категории, поиск по заказу/накладной,
отметки менеджера, страницы по 25/50 строк. Фильтры не изменяют общие счётчики.
Возврат к продажам сохраняет исходные параметры поиска, периода и страницы.
Данные перевозчика и пользовательский текст экранируются; URL возврата
разрешён только для локальных `/sales` и `/app/sales`.

Источник — тот же `api_sales_records`, что используется продажами: ручные
продажи, складские операции и исправления трекинга. Одна явно указанная
накладная объединяет товарные строки; без трека используется номер магазина.
Для продаж отдельный ключ кеша зависит от ссылки на отправление, а не от ID
товарной строки. Изменение трека не переносит прежний статус и заметки.
Остальные каналы не запрашиваются. Отменённые продажи без трека исключены.
GET читает кеш; ручное обновление — защищённый POST, плановое — CLI.

Сверка содержит все незавершённые отправления; вручённые — за 30 дней.
Старую вручённую накладную можно открыть напрямую из продажи. Категории
проблем пересекаются, но общий счётчик считает каждую накладную один раз.
Отсутствие ключа, неизвестные статусы, ошибки поиска, связи и старые данные
отображаются явно, не превращаются в «всё в порядке».

Правила: от 3 полных суток в ПВЗ — внимание, от 5 — срочно; последовательные
события готовности к выдаче не сбрасывают отсчёт. От 3 суток без новых событий
в пути — проверка. Промежуточный возврат на склад не означает возврат клиентом.
Порогами управляют `CDEK_PVZ_WARNING_DAYS`, `CDEK_PVZ_URGENT_DAYS`,
`CDEK_TRANSIT_WARNING_DAYS` (1–60 дней, срочный порог не ниже предупредительного).

Срок хранения и обещанная дата доставки не выводятся из предположений:
менеджер может внести подтверждённые СДЭК даты. Дата хранения действует до
конца указанного дня по МСК; за сутки до неё — срочно. Просроченная
подтверждённая доставка также срочная. Автоматическое получение этих двух
дат из API пока не реализовано; без даты отображается «срок уточнить».

Менеджер сохраняет заметку, «В работе», контакт сегодня/завтра. Контакт
назначается на календарный день МСК: наступил — внимание, прошёл — срочно.
«В работе» не скрывает проблему. Вручение получателю закрывает задачу по
доставке; полученный обратный заказ закрывает менеджер. Ошибки данных при
этом остаются видимыми. Подтверждать ещё не полученный возврат нельзя.
Локальные отметки хранятся в `CDEK_CACHE_DIR/reviews`, атомарно под тем же
межпроцессным lock. Версия записи предотвращает потерю параллельных правок;
при конфликте показывается несохранённая заметка. Миграций БД нет.
Доступ и изменения разрешены admin/employee через текущие проверки прав
ERP; POST дополнительно проверяет CSRF и наличие отправления в продажах.

### Карточка заказа

В карточке заказа Tictactoy добавлен блок «СДЭК»: накладная, исходный статус
перевозчика, город, дата события и история доставки. Время отображается в МСК.
Кнопка обновления доступна при настроенном ключе; GET карточки читает только
локальный кеш и не вызывает СДЭК. Ошибка связи сохраняет предыдущий статус,
показывает предупреждение и дату последней успешной проверки.

Запрос сначала использует явно заданную накладную из трекинга, иначе номер
заказа магазина. Ответ должен точно совпасть с запрошенным номером.
Поле трекинга, оплата, склад, бизнес-статус заказа и данные Bitrix не изменяются.
Wildberries исключён. Персональные данные получателя не сохраняются в кеше.
Из истории исключаются удалённые события, остальные сортируются по времени.
Возвратная накладная помечается отдельно. Несколько накладных на один заказ
пока не объединяются: при повторном использовании номера магазина следует
указать нужную накладную явно.

## Настройка и запуск после разрешения на выпуск

Переменные окружения web-процесса и фонового процесса:

- `CDEK_ACCOUNT` — Account из личного кабинета;
- `CDEK_PASSWORD` — Secure password;
- `CDEK_CACHE_DIR` — общий постоянный каталог кеша (по умолчанию `instance/cdek`);
- `ORDERS_DATABASE_PATH` — существующая база snapshot заказов;
- `CDEK_ORDER_OVERRIDES_PATH` — путь к локальным исправлениям трекинга для CLI
  (по умолчанию `instance/order_overrides.json`).

Секреты передаются через защищённую конфигурацию окружения сервера; в Git,
аргументы командной строки, JSON-ответы ERP и журналы их помещать нельзя.
Ключ считывается при старте процесса. Смена конфигурации требует перезапуска
web-процесса. Нового ключа, подписок и отправлений интеграция не создаёт.

Разовый запуск: `python -m scripts.cdek_delivery_sync`.
Подготовлены `deploy/systemd/vechasu-cdek-sync.service` и `.timer` по принятой
в проекте схеме WB. Перед установкой нужно проверить пути текущего release,
Python и EnvironmentFile на сервере и обеспечить один общий кеш для web и CLI.
Сервис и таймер автоматически этим изменением не устанавливаются.

CLI читает канонический список продаж через модуль приложения, затем snapshot
карточек заказов. Кеш карточек сохраняет прежний формат; одна накладная может
иметь отдельный кеш карточки и продаж. Несколько товарных строк продаж
не вызывают повторных запросов. Обоим процессам необходим один каталог кеша.

Таймер запускает проверку каждые 10 минут. Один проход ограничен 100 записями
и приблизительно 180 секундами плюс один текущий HTTP-запрос. Активные
отправления проверяются с интервалом от 10 минут, завершённые — раз в сутки,
ошибки поиска — не чаще раза в час. При большом числе заказов обновление может
занять несколько проходов; необработанные выбираются раньше проверенных.
HTTP 429 и ошибки авторизации/сети останавливают текущий пакет.
Ручные повторные запросы в течение минуты используют предыдущий результат.

Кеш — отдельные атомарно заменяемые JSON-файлы под общим межпроцессным lock;
миграция существующих баз не нужна. Повреждённый JSON не затирается.
Откат: остановить таймер, вернуть предыдущий release. Кеш можно оставить;
заказы и внешние системы изменений не получают.

## Проверки и ограничения

- Прямой разрешённый read-only smoke с существующим ключом: три реальные
  накладные и поиск по номеру магазина успешно вернули статусы и историю.
- `python -m unittest discover -s tests -p test_cdek_delivery.py -v`:
  транспорт, кеширование токена, ошибки, идентичность отправления, история,
  сохранность предыдущего статуса, права, CSRF, блокировка и периодический отбор.
- Локальный полный Flask/Jinja preview на синтетических данных: карточка заказа,
  ручное обновление и история, сохранение статуса при ошибке СДЭК; desktop и
  viewport 390×844. В консоли браузера ошибок и предупреждений не обнаружено.
- Проверены синтаксис Python 3.6 и `git diff --check`. Production Linux/systemd
  пока не проверялись; локальный preview использует штатную Windows-адаптацию
  тестового сервера, а новый CDEK lock проверен отдельным тестом Windows.
- Автоматический запуск на production и отображение реальных заказов в ERP
  требуют отдельного выпуска. Вебхуки пока не подключены; используется polling.
- Тесты `test_cdek_sales.py`: группировка, пороги ПВЗ, неизвестные статусы,
  подтверждённые сроки, возвраты, контакты, конфликты, ошибки кеша, CSRF,
  права, фильтры и пагинация, безопасный возврат, экранирование заметок.
- Flask smoke продаж Tictactoy/WB/Amazon и списка/деталей сверки выполнен
  в изолированном fixture с запретом сети. Новый экран в настоящем браузере
  в рамках реализации не проверялся; интерактивный макет проверялся ранее.
- Целевые проверки: 47 тестов CDEK, 7 тестов раскладки продаж и 8 тестов
  дизайн-системы продаж. Проверки выпуска требуют Linux: локальный
  `migration_preflight.py static-check` останавливается на отсутствующем
  Windows-модуле `fcntl`; `check_runtime_ddl.py` сообщает несовпадения путей
  и контрольных сумм существующих миграций в Windows checkout. Эти проверки
  не считаются пройденными; новые таблицы или миграции интеграция не создаёт.
